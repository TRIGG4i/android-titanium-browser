# Objective A: Enhanced Desktop must identify as Linux desktop

The existing Enhanced Desktop implementation currently spoofs Windows. Replace that coherent profile with a Linux desktop identity.

For Enhanced Desktop mode, make all externally observable UA surfaces agree with one another:

- HTTP `User-Agent`: desktop Linux, containing `X11; Linux x86_64`, no `Android`, no `Mobile`.
- `navigator.userAgent`: same Linux desktop identity.
- User-Agent Client Hints:
  - `navigator.userAgentData.mobile === false`
  - `navigator.userAgentData.platform === "Linux"`
  - `Sec-CH-UA-Mobile: ?0`
  - `Sec-CH-UA-Platform: "Linux"`
  - model empty
  - desktop form factor where supported
  - architecture/bitness coherent with x86_64 desktop semantics where Chromium exposes them
- `navigator.platform`: coherent Linux desktop value, preferably `Linux x86_64` or the exact Chromium desktop-Linux value generated by upstream code.
- Do not leave contradictory Windows strings in high entropy values or network headers.

Prefer Chromium's native desktop Linux UA construction paths over hand-built strings where possible.

Normal mobile mode must remain Android mobile and normal standard "Desktop site" behavior must not be accidentally changed unless required for consistency.

# Objective B: Portrait and landscape must expose the same desktop layout profile

The owner observes that Enhanced Desktop behaves differently in portrait and landscape. This must be removed.

The requirement is not merely "both are desktop UA". A site must choose the same desktop responsive breakpoint in either orientation.

Implement an orientation-independent logical desktop viewport for Enhanced Desktop mode.

Required behavior:

- `window.innerWidth` and `document.documentElement.clientWidth` must remain effectively identical across portrait and landscape for the same page, allowing at most a 1 CSS pixel tolerance unless Chromium requires a documented small offset.
- Both orientations must expose a desktop logical width of at least 1280 CSS px. Prefer a canonical width around 1365 or 1440 CSS px if that integrates cleanly with Chromium's existing desktop-site implementation.
- `matchMedia('(max-width: 768px)').matches` must stay `false` in both orientations.
- The profile must survive reload, redirects, history navigation, tab restore, process restart and per-site persistence.
- Do not implement this only with a one-shot JavaScript injection. It must live at the browser/WebContents/viewport layer so sites cannot trivially bypass it.
- Do not create inconsistent geometry where UA says desktop but viewport/screen/client metrics reveal a narrow phone.
- Keep touch input usable. The page may scale to fit the physical display, but the logical desktop layout must remain stable.

Adversarially inspect all relevant Chromium paths such as WebContents creation, WebPreferences, viewport meta processing, page scale, visual viewport, screen info and orientation updates. Choose the least invasive native solution.

# Objective E: Native virtual mouse / touchpad mode

Add an optional browser-level virtual mouse controlled by the phone touchscreen, with a feel close to a high-quality remote-desktop trackpad.

This is a real native browser feature, not a JavaScript cursor injected into pages.

UX requirements:

- Add a persistent but user-toggleable menu item, for example `Touchpad mouse` / `Virtual mouse`.
- When enabled, the touchscreen behaves as a relative trackpad rather than teleporting the cursor to the finger position.
- Smooth visible pointer overlay with frame-synchronized motion using Android's rendering primitives (`Choreographer` or equivalent) and no avoidable stutter.
- Pointer acceleration/smoothing tuned for small phone screens while preserving precision for small desktop controls.
- Single tap: primary/left click.
- Double tap-hold or another natural gesture: drag.
- Two-finger vertical/horizontal swipe: mouse-wheel style scrolling.
- Two-finger tap or long press: secondary/right click, provided it does not conflict badly with Android gestures.
- Pointer must be able to interact with web content accurately. Prefer a design that can also interact with browser UI where technically clean and safe.
- Cursor position persists while the mode remains active and is clamped correctly after rotation/window-size changes.
- Do not require Accessibility Service privileges merely to synthesize ordinary in-app input.
- Do not break text selection, software keyboard, back gestures, pinch zoom or normal touch navigation when the feature is disabled.

Implementation guidance:

- Use native Android input/event paths and Chromium ContentView/WebContents mouse-event paths.
- Generate proper mouse semantics (`SOURCE_MOUSE`, hover/move/button/scroll events or the native Chromium equivalent) rather than translating everything to fake touch taps.
- Render the cursor in a lightweight overlay owned by the activity/root compositor layer.
- Avoid per-frame allocations and main-thread work that can cause jank.

Add instrumentation or deterministic input tests for cursor movement, primary click, secondary click, drag and scroll. Measure that enabling the overlay does not introduce obvious frame jank on a modern ARM64 Android device.
